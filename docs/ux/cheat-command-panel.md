## 0. 为什么做这个面板（一句话）

> 这是全游戏**唯一的 USP**：玩家能用一句自然语言改规则。Core 里链路已齐全（`指令 → 意图解析 → JSON Patch → Schema 校验 → 生效`），但**表现层没有任何入口**——最独特的东西玩家碰不到，这是「游戏不够好玩」的最大原因。本面板就是把这套 Core 能力第一次交到玩家手里。

**本规格的硬约束**：所有行为必须与既有 Core 接口**对得上**，不得凭空发明字段。接口映射见 §10。

## 1. 设计哲学与「作弊张力」主张

### 1.1 MDA 三层

| 层 | 内容 |
|:--|:--|
| **机制 Mechanics** | 自然语言 → 意图分类（A/B/C/C+/D/E/F）→ JSON Patch → Schema 硬校验；业力按「分类价目 × 强度倍数 × 局势调整」定价（`KarmaEstimator`）；业力溢出触发识破增量 `Δ = C × O^α`（C 默认 0.1，α 默认 1.5），并即时结算一次。 |
| **动态 Dynamics** | 玩家在做**资源预算**：业力是有限燃料，识破是累积风险。稳健流＝小改规 + 靠棋艺消业滚雪球；赌徒流＝梭哈一波高溢出。技能树把「风险/成本」变成可投资的成长曲线。 |
| **美学 Aesthetics** | 掌握规则带来的**胜任感**、改写天规的**主宰幻想（Fantasy）**、天道注视下的**紧张（Challenge/Tension）**、以及业力承载的**道德重量（Narrative）**。 |

### 1.2 自我决定论（SDT）

- **自主性 Autonomy**：改规永远是**玩家的选择**，系统只负责把代价**透明可预期**（§6 代价透明）。绝不替玩家决定。
- **胜任感 Competence**：价目表、识破公式、力度档位**全部可见**，让玩家学会「精算」，从"乱试"升级到"我知道这手划算"。
- **关联感 Relatedness**：把「识破」人格化为**天道**——它不是一个概率数字，而是一个会注视、会判词、会降罚的角色（判词见 §7.5）。

### 1.3 心流平衡（Flow）

- 太便宜 → 改规成为**主导策略**，游戏无聊（张力=0）。
- 太贵 → USP 摸不到、玩家不敢用（张力=过载）。
- **目标区间**：让玩家**经常**处在「再改一手就要溢出」的**临界地带**，用「消业」把这根弦反复拉紧又放松，制造有节奏的紧张—释放循环。

### 1.4 「作弊张力」设计主张（本文档的核心裁决）

> **业力的安全阈值（`karma_max`，默认 120）就是张力旋钮。溢出是唯一的分水岭。**

| 档位 | 判据 | 代价 | 玩家体验 | 定性 |
|:--|:--|:--|:--|:--|
| **划算（安全施展）** | `当前业力 K + 本手代价 C ≤ karma_max`（不溢出） | 仅消耗"燃料"业力，**Δ=0，不触发结算** | "我精算过，这手白嫖" | ✅ 鼓励 |
| **临界（紧张施展）** | `K + C` 略超阈值（溢出 O 约 1–10） | `Δ = 0.1 × O^1.5`（O=5→≈1.1；O=10→≈3.2），结算基本不中 | "心跳加速，赌一把" | ✅ 核心体验区 |
| **危险（反噬）** | 溢出 O 较大（≥30） | O=30→≈16.4；O=60→≈46.5；O=100→**+100（必被识破）** | "完了，天道盯着我了" | ⚠️ 高风险 |
| **反噬后果** | 结算命中 | 识破概率**锁死清空**、结局路径转入「识破 / 天道审判」线，通关六道后触发**天道 Boss 战** | 「妄改天规者，罚入轮回」 | ❌ 惩罚而非禁止 |

**划算 vs 反噬的判定，UI 必须在确认前算清并直白告诉玩家**（§6）。这就是"系统让代价透明可预期"的落地。

**关于消业的反制节奏**：下棋事件会减业（象棋 `capture_pawn 8 / capture_medium 15 / capture_rook 25 / check 20 / checkmate 35 / pawn_cross 10`）。这让"作弊 → 认真下棋还债 → 再作弊"成为一条可持续的正循环，也是防「一波梭哈到底」的机制阀门。

**防主导策略检查（发现即标注为平衡缺陷）**：
- 若某条改规在不同局势下**恒为正收益且代价固定**，它就会变成万能解 → 必须保证定价随「分类 × 强度倍数 × 局势调整」动态浮动（Core 已实现）。
- ⚠️ **已知风险点**：`KarmaEstimator.AssessAsync` 对同一 `gameType:instruction:class` 有缓存（仅优化时延）。**规格要求：缓存不得改变"每次施展都重新扣除业力"的事实**；重复刷同一条指令不享受任何降价。quality-lead 需为此写用例（§12）。

## 3. 模块一：指令输入

### 3.1 入口形态（召唤方式）——**P0**

- **常驻按钮**：棋盘右下角固定「⚡ 改 规」按钮（P0，触控/鼠标都能用）。**常驻**是刻意的：USP 必须被看见，不能藏在菜单里。
- **快捷键**：`I` 键召唤/收起面板（P0，键位沿用原版习惯，与悔棋 `U` 不冲突）。
- **形态选择**：**底部抽屉**（P0，棋盘单列布局）／**右侧抽屉**（P1，宽屏/大地图模式）。抽屉而非独立弹窗——改规时**棋盘仍可见**（便于"选坐标"与预览高亮）。
- **收起点**：`Esc` 或点棋盘外部收起（P0，收起时若输入框非空，先弹"放弃这条指令？"确认）。

### 3.2 输入框形态与占位文案——**P0**

- 单行 `InputField`（P0），Enter 提交；多行 `TextArea`（P1，容纳长指令）。
- **占位提示文案（原文）**：

  > `输入一句话，改写这条棋规……例如：让我的马可以横着走`

- **辅助按钮**：`📍 选坐标`（P0，点击后在棋盘选格，自动把坐标文本插入输入框，沿用原版 `btn-insert-coord`）+ `⇄ 选区域`（P1）。象棋/围棋等需要指定点位的指令，光靠打字很难精确，这是降门槛的关键。
- 字符上限 200 字（P0，超出截断并提示「指令过长，最多 200 字」）。

### 3.3 示例指令陈列（降低「不知道能说什么」门槛）——**P0**

**陈列位置**：输入框正下方一行「试试」chips（可点击直接填入）。**覆盖六棋种**，且**每条都对应一个真实的意图分类**，让玩家第一眼就理解"能改什么"。

| # | 示例指令（原文） | 棋种 | 预期分类 | 演示点 |
|:--|:--|:--|:--|:--|
| 1 | `让我的马可以横着走` | 象棋 | C | 改走法（核心） |
| 2 | `把我的兵变成炮` | 象棋 | C | 换棋子 |
| 3 | `让我的车可以飞过楚河汉界` | 象棋 | C | 越过地形限制 |
| 4 | `让我落子时一次下两颗子` | 五子棋 | C/C+ | 改落子规则 |
| 5 | `让我的棋子被提掉后还能留在盘上` | 围棋 | C | 改提子规则 |
| 6 | `让我的老鼠可以吃掉大象` | 动物棋 | C | 改吃子等级 |
| 7 | `让我的棋子在六角星上可以连跳三格` | 跳棋 | C | 改跳跃距离 |
| 8 | `让我下的棋子这一回合不能被翻转` | 黑白棋 | C | 改翻转规则 |
| 9 | `让AI这一回合不能动` | 通用 | A | 机制修改 |
| 10 | `悔一步棋` | 通用 | A | 直接下命令 |

> 文案口径沿用原版 `试试："車变成两个"、"兵可以后退"、"象可以过河"` 的语气：短、口语、具体。

### 3.4 快捷预设 / 历史复用——**P0（历史）/ P1（收藏）**

- **最近 5 条历史**：本地环形缓存（P0），点击即回填输入框（不自动提交）。
- **「常用」收藏**：玩家可把一条指令**钉住**（P1，长按 chip → "收藏"），跨关卡保留。
- **技能解锁提示**：若历史里某条指令当前被技能树拦截（如 C+ 未解锁），chip 置灰并角标「🔒 需解锁『自定义棋子』」（P1）。

## 4. 模块二：处理中状态（异步 LLM）

> 意图解析是**异步 LLM 调用**（`OrchestratorEngine.ProcessCommandAsync` → `ParseIntentWithLogAsync` → `LlmClient.ChatAsync`），有延迟、可能失败。空转的等待必须被"演出来"。

### 4.1 加载态表达——**P0**

- **遮罩 + 卡片**（沿用原版 `thinking-overlay` 模式）：棋盘半透明锁定、输入框禁用，中央卡片显示。
- **阶段文本**（取自 `OrchestratorEngine.ThinkingStage`：`intent` → `code`）：
  - `intent` 阶段 → `◐ 天道正在推演你的妄念…　阶段：意图解析`
  - `code` 阶段 → `◐ 正在改写规则的因果…　阶段：规则生成`
- **计时**：卡片左下角实时显示 `已用时 2.4s`（P1，给玩家"系统还活着"的确定感）。
- **禁用规则**：处理中禁止再次提交、禁止走子（P0，避免并发改规导致 configs 竞态）。

### 4.2 超时阈值与重试——**P0**

| 场景 | 阈值 | UI 行为（文案原文） |
|:--|:--|:--|
| 软提示 | 8s | 卡片副标题追加 `仍在推演…天道有时也会迟疑`（不打断） |
| 硬超时 | **20s**（P0） | 终止本次调用（`CancellationToken`），进入下述失败态 |
| 超时提示 | — | `⚠️ 天道迟迟没有回应（已等待 20 秒）。` 按钮：`重新施展` / `改用预置指令` |
| 失败重试 | — | `重新施展` 按钮可重试 **1 次**；第 2 次仍失败 → 自动引导到预置指令集（§9） |

> **实现注记**：`LlmClient.ChatAsync` 自带 `timeoutSeconds`（默认 120s）。UI 侧的 20s 是**产品级超时**，应通过传入 `CancellationToken` 主动取消，而**不是**依赖 HTTP 超时（否则玩家要干等 2 分钟）。

### 4.3 边缘情况——**P0**

1. **连续提交**：处理中禁用输入与按钮；重复按 Enter 无副作用（幂等）。
2. **切屏/暂停**：处理中切到后台或返回 hub（`GameScreen.Detach()`）时，**取消进行中的调用**并清空面板状态，避免回调落到已销毁的会话上。
3. **AI 回合期间改规**：若当前是 AI 思考中（`GameSession.IsAiTurn`），面板可打开但施展按钮置灰，副标题 `轮到对方时无法改规，请稍候`（P1）。

## 5. 模块三：改规预览（关键 · 生效前的确认）★

> **Core 事实**：`ProcessCommandAsync` 返回的 `result["modified_configs"]` 是**全新的完整配置**（键为 `board_state` / `pieces_red` / `pieces_black` / `rules` / `ui_config` / `board`），**引擎本身不会改动当前对局**——生效与否由调用方决定。这正是"先预览、后确认"的天然支点。

### 5.1 人读 diff 呈现规则——**P0**

- **生成方式**：对每个 `modified_configs[k]`，用 `JsonPatch.GenerateDiff(旧配置[k], 新配置[k])` 得到补丁数组，再把每条 `{op, path, value}` **翻译成人话**（不得直接显示原始 JSON Pointer）。
- **格式**：`改前 → 改后` 的**对照卡片**，一条改动一张卡：

  ```
  ┌ ① 走法修改 · 红方·马 ──────────────────────────────┐
  │  马（红）：  走日字（斜走一格）        →   走日字 或 横走一格  │
  │  ↗ 影响：你的马多出 4 个横走落点                     │
  └──────────────────────────────────────────────────┘
  ```

- **中文动词映射（P0，工程按此表落地）**：

| 目标配置 | 字段路径 | 人读措辞模板 |
|:--|:--|:--|
| `pieces_*` | `*.move` / 原语 | `{棋子名}：{旧走法} → {新走法}` |
| `pieces_*` | `*.type` / `*.name` | `{棋子}：{旧类型} → {新类型}（改名：{新名}）` |
| `board_state` | `pieces[].position` | `{棋子}：({x1},{y1}) → ({x2},{y2})` |
| `board_state` | `pieces[].is_alive` | `{棋子}：在场 → 移除` |
| `rules` | `win_conditions.*` | `胜利条件：{旧} → {新}` |
| `ui_config` | 颜色/尺寸 | `外观：{棋子} {旧} → {新}` |

- **棋盘联动高亮（P1）**：预览时，受影响的棋子在棋盘上以**幽灵/虚线**样式描边（区别于常规选中高亮），位置变化画箭头。

### 5.2 「预览 vs 已生效」的视觉区分——**P0（硬要求）**

| 状态 | 面板外框 | 角标 | 棋盘 | 列表归属 |
|:--|:--|:--|:--|:--|
| **预览态** | 琥珀色虚线框、整体 90% 不透明 | 右上角 `预览` 徽章 | 幽灵高亮、原棋子仍按旧规则可动 | 不进入「已激活规则」 |
| **已生效态** | 常态实线框 | 无徽章 | 实色、新规则即刻生效 | 进入「已激活规则 / 已激活机制」 |

> **禁止**：预览态的改动绝不能提前写进 `configs`（否则出现"还没确认，马已经能横走"的错觉）。预览数据只存在于面板的临时快照里。

### 5.3 预览底部操作区——**P0**

```
┌──────────────────────────────────────────────────────────┐
│  业力代价：30　识破风险：+0%（未溢出）                      │ ← §6 代价透明
│         [ ✕ 取消 ]              [ ✓ 确认施展 ]           │
└──────────────────────────────────────────────────────────┘
```

- 主按钮文案随风险变化（§6）：低危 `✓ 确认施展`；高危 `⚠️ 强行施展（将溢出 32 点）`。
- `取消` → 丢弃快照，回到空闲（不扣业力；`KarmaEstimator` 评估过的成本**不会**被扣除，因为扣费发生在"确认"之后，见 §10 集成顺序）。

### 5.4 边缘情况——**P0**

1. **部分成功（`type == "partial"`）**：多 action 中部分失败。预览必须**分条标注**：成功项正常卡片 + ✅；失败项红色卡片 + ❌ 及失败原因（§8），并在顶部提示 `本指令 2 项中 1 项无法实现，已为你保留可行部分`。
2. **跨配置联动冲突**：同一改动同时命中 `board_state` 与 `pieces_red`（如"把我的马变成炮"既改类型又改走法）。预览需合并为**一张卡**，避免玩家以为改了两处。
3. **空 diff**：`modified_configs` 无实质变化（`op` 为空）→ 不进入预览，直接提示 `天道觉得这和你现在的棋规没什么两样`（对应引擎 `type == "success"` 无 modified_configs 的情形）。

## 6. 模块四：确认 / 撤销（两个撤销栈）★

### 6.1 二次确认设计——**P0**

- **低危**（不溢出）：预览页点「✓ 确认施展」即生效，**不再二次弹窗**（避免操作疲劳；代价已在 §6 透明展示）。
- **高危**（溢出，会累积识破）：**强制二次确认**（P0），弹窗文案原文：

  ```
  ⚠️ 此举将超出业力安全线

  施展「让我的车飞过河」将消耗业力 55，使你从 92 溢出到 147（超出安全阈值 120 共 27 点）。
  天道的怀疑将增长约 +14.0%。一旦被识破，本道余下棋局将无法再作弊。

  [ 再想想 ]                                    [ 我意已决，施展 ]
  ```

  - 「再想想」默认聚焦（避免误触），「我意已决」为红色危险样式（P0）。

### 6.2 两个撤销栈如何共存（关键澄清）——**P0**

本游戏里存在**两条彼此独立的历史**，绝不可合并：

| 撤销栈 | 内容 | 触发 | Core 落点 |
|:--|:--|:--|:--|
| **棋局栈（棋谱）** | 每一手落子/走子 | `悔棋`（`U` 键 / HUD 按钮） | `GameSession.UndoLastMove()` |
| **改规栈（规则）** | 每一次**已生效**的改规配置快照 | `撤回AI修改`（原版 `btn-undo-config`） | 表现层保存的 `configs` 快照栈 |

**规则（P0，逐条明确）**：

1. **互不干涉**：悔棋只回退棋谱，**不撤销任何改规**；撤回改规只回退规则，**不回退棋谱**。
2. **独立深度**：改规栈建议上限 **10 层**（P1，超出丢最旧）；棋局栈沿用 `GameSession` 现状。
3. **规则回退 ≠ 局面回退**：若在改规后已走子，再撤回该改规，可能出现"当前局面与规则不匹配"（例如"兵可后退"改规被撤回，而兵已被退回过）。**必须给出提示（P0）**：

   > `⚠️ 你在这条改规之后已经走过棋。撤回规则不会回退棋局，当前局面可能与旧规则不完全一致。是否继续？`

4. **改规入谱标记（P1，强烈建议）**：在 `move_history` 中插入一条 `type:"rule_change"` 标记（不改棋盘、不占回合）。这样悔棋回到标记点前时，可提示 `此处之后有一次改规，是否一并撤回？`，把两个栈在**体验上**缝合，但**数据结构上仍分离**。
5. **撤回AI修改按钮状态**：改规栈为空时置灰，悬停提示 `没有可撤回的改规`。
6. **代价不回滚**：⚠️ 已消耗的业力与已累积的识破概率**不因撤回而返还**（世界观自洽：妄念已生，业已记下）。按钮旁常驻小字 `（撤回不返还业力）`（P0）。

### 6.3 边缘情况——**P0**

1. **改规后立刻悔棋**：允许，按规则 1 各走各的栈。
2. **改规栈为空**：按钮置灰（§6.2.5）。
3. **一指令多 action**：一次施展产生多处改动 → 记为**一个**改规快照（整批撤回），不拆散。
4. **撤回后重放**：撤回的改规应进入"最近历史"，便于一键复现（P1）。

## 7. 模块五：失败反馈（必须解释「为什么不行 / 怎么改能行」）★

> 反例（禁止）：`❌ 非法指令`。正例（必须）：
> ```
> ⚠️ 马走日无法直接改为横走
> 原因：象棋的「马」由固定走法生成，横走会与「车」的规则冲突。
> 建议：改为「马可以走日字，或直走一格」，是否采用？   [ 采用建议 ] [ 手动修改 ]
> ```

### 7.1 引擎结果 → 文案映射表——**P0**

`ProcessCommandAsync` 返回的 `type` 决定分支；`message` 为引擎原文。表现层**必须**把技术性 `message` 包装成"原因 + 出路"结构。

| 引擎返回 | 触发条件 | UI 标题（原文） | 正文（原因） | 出路按钮 |
|:--|:--|:--|:--|:--|
| `type=="rejected"` + `feasible:false` | 意图判定不可行 | `⚠️ 这一步天道改不动` | 引擎 `message` / `intent.response_to_player`（如"马走日无法改为横走"） | `采用建议`（若意图含替代）/ `手动修改` |
| `type=="rejected"` + 技能拦截 | `allowed_classifications` 不含该分类 | `🔒 此术尚未解锁` | 如 `C+ 类需在技能树解锁「作弊精通 → 自定义棋子」` | `前往技能树` / `换个指令` |
| `type=="rejected"` + `karma_blocked:true` | `estimated_karma_cost > 单次上限` | `🚫 业障过重，天道不容` | 引擎原文：`作弊业力评估为 {C} 点，超出单次上限 {S} 点，天道拦截·不予执行` | `拆成两小步`（引导分解）/ `取消` |
| `type=="error"` + Schema 校验失败 | `SchemaValidator` 拒绝 | `⚠️ 这规则自相矛盾` | 把 `[pieces.0.position.0] 12 超出棋盘范围 (0-8)` 转成 `棋子坐标超出棋盘（横 0–8，纵 0-9）` | `看看建议` / `手动修改` |
| `type=="error"` + `"未设置API密钥"` | `!Client.IsAvailable` | — | **直接转入降级模式（§9）** | `打开预置指令` |
| `type=="error"` + 超时/网络 | `LlmResult.Ok==false` | `⚠️ 天道迟迟没有回应` | `已等待 {n} 秒，或网络不通` | `重新施展` / `改用预置指令` |
| `type=="error"` + 意图无法解析 | `intent==null` | `🤔 天道没听懂这句话` | `无法解析这句话的意图` | `换个说法` / `打开预置指令` |
| `type=="fun"` | E 类闲聊 | 无错误样式（绿色气泡） | 直接显示 `message` | — |

### 7.2 Schema 校验错误的人读翻译——**P0**

`SchemaValidator` 返回形如 `"[路径] 描述"` 的错误串（`;` 分隔）。必须逐条翻译：

| 原始错误（示例） | 翻译后（原文） |
|:--|:--|
| `[pieces.0.position.0] 12 超出棋盘范围 (0-8)` | `有棋子的横坐标超出了棋盘（范围 0–8）` |
| `[pieces.3.position.1] 11 超出棋盘范围 (0-9)` | `有棋子的纵坐标超出了棋盘（范围 0–9）` |
| `棋子丢失: red_rook_1` | `改动会让「红车」意外消失，这不合理` |
| `棋子属性被篡改: h1的side从red变为black` | `改动会把「红马」变成黑方棋子，天道不允许颠倒阵营` |
| `缺少 side_overrides 字段，该字段必须保留` | `规则改动缺少必要结构（side_overrides），无法生效` |

### 7.3 「怎么改能行」的引导建议——**P1**

- 对**常见拒绝模式**维护建议模板库，随错误渲染 `采用建议` 按钮，一键把建议文本填入输入框：
  - 不可行 → `改为「马走日字，或直走一格」` / `改为「消耗 50 业力换取一次额外行动」`。
  - 业力超上限 → `拆成两小步：先把业力降到 60 以内再改`。
  - 未解锁 → `（锁定）需技能点 ×N 解锁「自定义棋子」`。

### 7.4 失败反馈样式——**P0**

- 红色边卡片，保留玩家原指令（可点"编辑重试"回填输入框）。
- **不弹全屏遮挡**（除识破结局弹窗）——失败要轻，避免打断心流。
- 每次失败都写一条 `addMessage`（沿用原版消息流），可回溯。

### 7.5 边缘情况——**P0**

1. **多错误同时返回**：逐条列出（最多 3 条，超出折叠"还有 N 条…"）。
2. **错误串本身无法翻译**：回退为"未知校验错误"，并把原始串放在可展开的"技术详情"里（P1，便于 quality-lead 抓 bug）。
3. **E 类被误判为修改**：若玩家只是问"谁现在占优"，引擎应回 `type=="fun"` 且 `response_to_player` 是棋局解读——UI 用普通对话气泡显示，**不弹预览**（P0）。

## 8. 模块六：代价透明（施展前展示预估）★

> 玩家掌舵 = 代价必须**在确认之前**算清。数据来源见 §10。

### 8.1 三个必显指标——**P0**

预览页底部常驻一行"代价条"：

```
┌ 代价预估 ────────────────────────────────────────────────┐
│  ☯ 业力代价   30        （68 → 98，安全线 120）          │
│  👁 识破风险   +0%       （未溢出，不会触发结算）          │
│  ⚖️ 局面影响   你的马多出 4 个横走落点，对攻能力上升       │
└──────────────────────────────────────────────────────────┘
```

| 指标 | 计算（变量+单位） | 来源 |
|:--|:--|:--|
| **业力代价 C** | 引擎返回 `result["estimated_karma_cost"]`（单位：点，1–120） | `OrchestratorEngine` |
| **溢出量 O** | `O = max(0, K_cur + C − K_max)`（点） | 表现层用 `KarmaAssessor.GetLocalKarma()/GetLocalKarmaMax()` 计算 |
| **识破增量 Δ** | `Δ = C_coef × O^α`（C_coef 默认 0.1，α 默认 1.5；单位：百分点） | `KarmaAssessor.CalculateDetectionDelta(O, skillModifiers)` |
| **识破风险** | `O ≤ 0` → `+0%（不结算）`；`O > 0` → `+min(100, Δ)%`，并注明"施展后立即结算一次" | 同上 |
| **局面影响** | 由 diff 摘要归纳（如"多 N 个落点""移除 1 子"） | 表现层解析 preview |

### 8.2 三档代价的呈现文案——**P0**

| 档位 | 代价条样式 | 文案 |
|:--|:--|:--|
| 划算 | 绿色 | `☯ 业力代价 30（68 → 98，仍在安全线内）` · `👁 识破风险 +0%` |
| 临界 | 琥珀 | `☯ 业力代价 45（92 → 137，将溢出 17）` · `👁 识破风险 +7.0%（施展后立即结算）` |
| 危险 | 红色 + 抖动动画（P1） | `☯ 业力代价 90（110 → 200，将溢出 80）` · `👁 识破风险 +71.6%（极高，几乎必被识破）` |

### 8.3 技能/道加成透明——**P0**

若玩家技能使成本/风险下降，显式标注"省了多少"，强化成长正反馈：

> `☯ 业力代价 30（原 40，『效率欺诈』-10）`
> `👁 识破风险 +7.0%（原 10.0，『藏锋』系数 0.07）`

（对应 `skillModifiers` 中 `efficiency_fraud` / `hell_hungry_discount` / `heaven_asura_discount` / `detection_coefficient` / `detection_alpha` 等字段。）

### 8.4 边缘情况——**P0**

1. **低危/免费作弊**：若 `free_cheat_count > 0`（作弊精通·白嫖），显示 `☯ 本手免费（『白嫖』剩余 1 次）`，并提示"透支时仍有惩罚"。

| 6 | `悔一步棋` | 通用 | A | 30 | 触发 `GameSession.UndoLastMove()`（不入改规栈） |
| 7 | `让我的棋子被提掉后还能留在盘上` | 围棋 | C | 50 | 提子规则关闭（`capture` 禁用） |

### 10.4 边缘情况——**P0**

1. **中途断网**：已进预览的照常确认生效（补丁已在本地）；再次施展才进入降级。
2. **预置与当前棋种不匹配**：按当前 `GameType` 过滤预置列表（象棋局不显示围棋预置）。

### 11.1 ⚠️ 关键集成顺序（工程易错点）

`OrchestratorEngine.ProcessCommandAsync` **只做预估，不改动业力/识破状态**。因此确认施展的完整顺序必须是：

```
1. 读当前 RPG 状态 → 同步到预估器：
   KarmaAssessor.SetLocalKarmaState(karma, karmaMax, singleMax)
   KarmaAssessor.SetRealmDetection(detection, realm)
2. 调 ProcessCommandAsync  → 得到 estimated_karma_cost / modified_configs / type
3. 校验通过 → 进入预览（此时什么都没变）
4. 玩家点「确认施展」：
   a. 记录改规快照（旧 configs 入改规栈）
   b. 用 modified_configs 覆盖当前 configs → 刷新棋盘/规则
   c. SamsaraEngine.IncreaseKarma(cost) → 取 (actual, isOverdraft, overshoot)
   d. 若 isOverdraft → SamsaraEngine.Detection.HandleOverdraft(overshoot)
   e. detected → §9.3 弹窗；否则刷新 HUD
5. 回传预估器：KarmaAssessor.SetLocalKarmaState(新业力, ..., ...)
```

> **顺序错误会出现的 bug**：先扣业力再预览 → 玩家取消后业力白扣；不同步预估器 → 单次上限门控与识破预估全错。

## 13. 边界情况总览与已知风险

### 13.1 边界情况（至少覆盖三类）

1. **输入类**：空/超长(>200)/含 Emoji/含坐标占位/疑似注入（Prompt Injection）——一律原样透传给引擎，但对返回结果做严格 `ExtractJson` 容错（Core 已实现，UI 只需优雅展示解析失败）。
2. **并发类**：处理中重复提交、处理中切屏、处理中走子、AI 回合中改规。
3. **状态类**：改规栈空/满、改规后走子再撤回、识破锁死、换道重置、部分成功（partial）。
4. **降级类**：无密钥进入、中途断网、预置与棋种不匹配、恢复联网。
5. **数值类**：免费作弊、技能折扣、低危不溢出、高危必溢出。

### 13.2 已知风险与取舍

| 风险 | 说明 | 处置 |
|:--|:--|:--|
| **预览一致性** | 预览用的是 LLM 生成的 `modified_configs` 快照；若其间棋局变化，快照可能过时 | P0：进入预览即锁定走子；确认前重新校验一次 `SchemaValidator` |
| **UX 认知过载** | 代价条 + diff + 双撤销栈信息量大 | P0：低危路径简化（不弹二次确认）；高危才展开全部信息 |
| **张力漂移** | 若玩家解锁大量减费技能，"临界地带"可能被永久绕过，张力消失 | 平衡巡检：统计平均溢出分布；必要时上调 `karma_max` 或收紧技能折扣（数值归设计守门） |
| **离线补丁失真** | 预置补丁是手写模板，可能与 Core 规则演进脱节 | 预置补丁纳入 L1 回归（`SchemaValidator` 必须通过），随 Core 变更同步 |
| **业力不可回滚** | 撤回改规不返还业力，可能引发"我白扣了"的困惑 | 文案前置（按钮旁常驻"撤回不返还业力"），并把该规则写进教程 |

## 14. 与世界观 / 叙事的结合（六道轮回）

- **业力不是数值惩罚，是道德选择**：每一次施展都在"堕落值 / 悟道值"（`alignment.enlightenment / corruption`）与结局判定上留痕（`EndingSystem`：`exposed / true_me / enlightenment / corruption / samsara`）。
- **天道是角色**：识破判词（`DetectionModel`）与重置判词让"概率"人格化——玩家不是输给随机数，而是被一个"看见一切"的对立面裁决。
- **面板语气**：全程用"天道 / 妄念 / 因果 / 业障"的口吻（见各节文案），让"改规"既是机制操作，也是**向六道举刀**。
- **代价透明即叙事**：系统把"你这手会有多重"提前告诉玩家，等价于"天道把因果摆在你面前，选择权仍在你"——这正是本作"玩家掌舵"哲学与"六道轮回"主题的合流点。
