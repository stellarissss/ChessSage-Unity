## 1. 项目概述与核心理念

### 1.1 项目愿景

**无限制象棋**是一款突破传统规则束缚的创新型中国象棋游戏。核心创新点在于：

> **玩家可以通过自然语言指令，实时修改游戏规则、棋盘状态、棋子能力，甚至游戏界面本身。**

这不是一款普通的象棋游戏，而是一个**规则可塑的、活的**游戏系统。

### 1.2 核心玩法

| 阶段 | 描述 |
|-|-|
| **正常对弈** | 玩家与AI进行标准中国象棋对局 |
| **输入指令** | 玩家随时在输入框输入自然语言指令（如"让我的马可以斜着走"、"把車变成两个"、"我要悔三步棋"） |
| **AI解析** | 系统通过多级AI协作，解析玩家意图并分类 |
| **代码生成** | 第二级AI根据分类生成JSON Patch或HTML修改 |
| **校验执行** | Schema校验 + 规则验证，通过后应用到游戏 |
| **实时生效** | 修改即时应用到游戏中，无需重启 |

### 1.3 技术栈

| 层级 | 技术 |
|-|-|
| 前端层 | HTML5 + CSS3 + 原生 JavaScript (ES2022+)，移动端优先响应式设计 |
| 后端层 | Python 3.11+ / FastAPI / Uvicorn，HTTP API 通信 |
| AI层 | DeepSeek API（deepseek-flash，模型名统一取自根 `config.json`），二级AI协作（意图解析→代码生成） |
| 规则引擎 | jump/ray 双原子移动体系 + where 条件表达式引擎 |
| 存储层 | 内存状态 + JSON配置文件持久化 + 撤销栈 |
| 校验层 | JSON Schema (Draft7) + 规则变化检测 |

### 1.4 设计哲学

- **🌟 灵活编码（最高纲领）**：项目以"用AI现场生成代码实现大部分要求"为核心创新形式。除已完成的硬编码部分外，所有新功能皆不可以用硬编码实现，必须用AI编码实现（如棋盘旋转、自定义棋子等）。为此可以牺牲稳定性、token花销、速度等，因为灵活编码是项目设立的初衷。
- **JSON驱动架构**：所有可变元素（规则、棋盘、棋子）都抽象为JSON数据，游戏引擎从JSON读取配置，AI只需修改JSON即可改变游戏行为；配置在进程内缓存、每类只读一次，仅在 AI 修改成功应用、重置/重开/关卡等显式规则变更后才会重新读盘，走棋 / valid_moves / AI 计算不重复读盘。
- **jump/ray 原子体系**：将所有棋子的移动规则解构为 jump（离散跳跃）和 ray（射线滑行）两种底层原子，配合 where 条件表达式，使 AI 能够修改规则概念本身。
- **JSON Patch优先**：AI输出RFC 6902标准的JSON Patch操作数组，而非全量JSON，减少token消耗和出错概率。
- **最小改动原则**：AI修改时只改动最必要的部分，通过区段标记系统实现HTML精准替换。
- **多级校验**：Schema校验 → 规则验证 → 范围检查，多重保障修改质量。
- **可撤销**：所有AI修改都进入撤销栈，玩家可随时撤回。

### 2.2 分类体系详解

| 分类 | 名称 | 处理方式 | 修改目标 | 说明 |
|-|-|-|-|-|
| A | 机制修改 | A1硬代码 + A2 CodeAI | board_state.json + rules.json | A1: 悔棋/输赢（硬编码）；A2: 游戏机制+AI性格（灵活编码，原子原语组合） |
| B | 棋盘变换 | CodeAI | board_state.json | 添加/删除/移动棋子、修改棋子属性 |
| C | 规则修改 | CodeAI | pieces.json | 修改棋子移动方式、添加特殊能力、阵营专属规则 |
| C+ | 自定义棋子 | CodeAI | pieces.json + board_state.json | 创建全新棋子类型，AI生成规则和棋盘实例 |
| B+C | 棋盘+规则 | CodeAI×2 | board_state + pieces.json | 先B后C，B的修改结果传入C |
| D | 界面修改 | CodeAI | board.json / ui_config.json / index.html | D1子类改配置，D2子类改HTML结构 |
| E | 搞笑 | 硬代码 | 无 | 幽默回复，不修改任何配置 |
| F | 高级功能 | 不可行 | - | 需要修改核心引擎代码的请求，标记不可行 |

**A类子分类详解：**
| 子类 | 名称 | 处理方式 | 修改目标 | 说明 |
|-----|------|---------|---------|------|
| A1 | 硬编码操作 | 硬代码 | board_state.json | 悔棋（undo_move）、设置赢家（set_winner） |
| A2 | 机制修改 | CodeAI | board_state.json + rules.json | 游戏机制原语 + AI性格系统，原子化组合实现 |

### 2.3 D1与D2子类判断

- **D1 (配置文件修改)**：`structured_instruction` 中**不含** `target_sections` 字段 → 修改 `board.json`（棋盘外观）或 `ui_config.json`（全局主题）
- **D2 (HTML结构修改)**：`structured_instruction` 中**含** `target_sections` 字段 → 通过区段替换修改 `index.html`（增删改DOM元素）

### 3.2 pieces.json — 棋子移动原语（核心创新）

采用 **jump + ray** 两种原子移动原语定义所有棋子的移动规则。这是 v4.0 架构的核心创新。

```
pieces
├── _metadata: {version, description}
├── pieces:                   # 预定义棋子（7种标准棋子）
│   ├── general: {
│   │   label: {red: "帥", black: "將"},
│   │   is_king: true,
│   │   moves: [
│   │     {
│   │       kind: "jump",         // 移动原子类型
│   │       to: [0, 1],           // jump: 目标偏移
│   │       block: [],            // jump: 关卡格（必须为空）
│   │       land: "any",          // 落点要求: empty/enemy/any
│   │       sym: "rotate4",       // 对称展开: none/rotate4/rotate4_mirror/mirror_x
│   │       where: [              // 条件表达式（额外约束）
│   │         {in_region: "$dest", region: "$palace"}
│   │       ]
│   │     }
│   │   ]
│   │ }
│   ├── advisor: {...}
│   ├── elephant: {
│   │   moves: [{
│   │     kind: "jump",
│   │     to: [2, 2],
│   │     block: [[1, 1]],       // 象眼阻挡
│   │     sym: "rotate4",
│   │     where: [
│   │       {not: {crossed_river: "$dest", by: "$side"}}
│   │     ]
│   │   }]
│   │ }
│   ├── horse: {
│   │   moves: [{
│   │     kind: "jump",
│   │     to: [1, 2],
│   │     block: [[0, 1]],       // 马腿阻挡
│   │     sym: "rotate4_mirror"
│   │   }]
│   │ }
│   ├── chariot: {
│   │   moves: [{
│   │     kind: "ray",            // 射线滑行
│   │     dir: [1, 0],           // ray: 方向向量
│   │     max: -1,               // ray: 最大步数（-1=无限）
│   │     screens: 0,            // ray: 需跳过的棋子数（炮架）
│   │     land: "any",
│   │     sym: "rotate4"
│   │   }]
│   │ }
│   ├── cannon: {
│   │   moves: [
│   │     {kind: "ray", dir: [1,0], max: -1, screens: 0, land: "empty", sym: "rotate4"},  // 移动（空落点）
│   │     {kind: "ray", dir: [1,0], max: -1, screens: 1, land: "enemy", sym: "rotate4"}   // 吃子（隔1子）
│   │   ]
│   │ }
│   └── soldier: {
│       moves: [
│         {kind: "jump", to: "$forward", block: [], land: "any", sym: "none"}, // 前进
│         {                                                                   // 过河后横走
│           kind: "jump", to: [1,0], block: [], land: "any", sym: "mirror_x",
│           where: [{crossed_river: "$self", by: "$side"}]
│         }
│       ]
│     }
├── side_overrides: {           # 阵营专属覆盖规则
│   red: {},                    // key为棋子type, value为覆盖字段
│   black: {}
│ }
└── custom_pieces: []            # 自定义棋子类型数组
```

#### 移动原子详解

**jump（离散跳跃）**：
- `to`: `[dx, dy]` 相对偏移，或 `$forward`（向前，根据阵营自动确定方向）
- `block`: `[[dx, dy], ...]` 关卡格列表——这些格子必须为空才能跳过去（马腿、象眼）
- `land`: `"empty"`(只能落在空格) | `"enemy"`(只能吃敌方) | `"any"`(任意)

**ray（射线滑行）**：
- `dir`: `[dx, dy]` 方向向量（单位向量）
- `max`: 最大步数（`-1` = 无限）
- `screens`: 需要跳过的棋子数（炮架机制，0=不能跳子，1=隔1子吃，2=隔2子吃）
- `land`: 落点要求

**通用字段**：
- `sym`: 对称展开方式
  - `none`: 不展开，原样使用
  - `rotate4`: 4向旋转（上下左右）
  - `rotate4_mirror`: 4向旋转+镜像（8方向）
  - `mirror_x`: 水平镜像（左右对称）
- `where`: 条件表达式列表（额外约束，详见 3.2.1 节）

#### where 条件表达式

条件表达式用于约束移动的额外条件，支持逻辑组合：

| 条件原语 | 语法 | 含义 | 示例 |
|-|-|-|-|
| `in_region` | `{"in_region": "$dest", "region": "$palace"}` | 目标在指定区域内 | 将/士只能在九宫 |
| `crossed_river` | `{"crossed_river": "$self", "by": "$side"}` | 是否已过河 | 象不能过河 |
| `not` | `{"not": {...}}` | 否定条件 | 象的过河约束取反 |
| `and` | `{"and": [{...}, {...}]}` | 与条件 | 多个条件同时满足 |
| `or` | `{"or": [{...}, {...}]}` | 或条件 | 任一条件满足 |
| `same_side` | `{"same_side": "$dest"}` | 目标在己方区域 | |
| `has_property` | `{"has_property": "$self", "key": "flying"}` | 棋子有某属性 | 自定义棋子能力 |

**变量引用**：
- `$self`: 当前棋子位置
- `$dest`: 目标位置
- `$side`: 当前棋子阵营（red/black）
- `$opponent`: 对方阵营
- `$palace`: 己方九宫格区域
- `$forward`: 前进方向（红方[0,-1], 黑方[0,1]）

**side_overrides 合并机制**：引擎深拷贝默认棋子规则，然后用阵营覆盖字段递归合并（dict递归合并，list/标量整体替换）。只需包含需要覆盖的字段，其他自动继承。

## 4. AI系统详细设计

### 4.1 第一级：意图解析AI (Intent Parser)

**模型**: deepseek-flash（取自 config.json）
**温度**: 0.3
**系统提示词**: `INTENT_PARSER_SYSTEM` (定义于 prompts.py)

**输入**: 玩家自然语言指令 + 上下文
**输出**: 结构化JSON

```json
{
  "classification": "A|B|C|C+|D|E|F|B+C",
  "feasible": true,
  "confidence": 0.95,
  "reasoning": "判断理由",
  "target_files": ["board_state.json"],
  "structured_instruction": {
    "action": "add_piece",
    "target": "pieces",
    "parameters": {"type": "chariot", "side": "red", "position": [4, 4]},
    "constraints": []
  },
  "response_to_player": "给玩家的回复",
  "next_ai_prompt": "传递给第二级AI的完整提示词"
}
```

### 4.2 第二级：代码生成AI (Code Generator)

**模型**: deepseek-flash
**温度**: 0.1~0.3（分类不同，温度不同）
**输出格式优先**: RFC 6902 JSON Patch 数组

**分类专家提示词**（定义于 prompts.py）：
- `BOARD_TRANSFORMER_SYSTEM`: B类棋盘变换AI
- `RULE_MODIFIER_SYSTEM`: C类规则修改AI
- `PIECE_CREATOR_SYSTEM`: C+类自定义棋子AI
- `UI_MODIFIER_SYSTEM`: D类界面修改AI

### 4.3 JSON Patch 优先策略

AI 优先输出 JSON Patch（RFC 6902）而非全量JSON，原因：
1. **Token效率高**：只描述变化，不重复未修改内容
2. **精确度高**：Patch操作语义明确，减少AI误改其他字段
3. **便于审计**：操作记录清晰，便于前端展示修改历史
4. **回滚方便**：反向Patch即可撤销

**Patch操作类型**：
- `add`: 添加字段/数组元素
- `remove`: 删除字段/数组元素
- `replace`: 替换字段值
- `move`: 移动字段
- `copy`: 复制字段

### 4.4 校验与重试机制

> **设计决策**：项目不使用独立的"校验AI"。理由：(1) 校验AI采用fail-open策略，
> 实际无法有效拦截错误输出；(2) 玩家可通过撤销机制自行处理AI的错误输出；
> (3) 硬编码检查（Schema + 业务规则）足以防止运行时错误。校验完全依赖硬编码实现，
> 仅在输出解析失败或Schema/业务校验失败时触发重试。

```
AI输出
  │
  ▼
JSON格式解析 ──失败──► 重试 (温度+0.1)
  │
  ▼ 成功
JSON Schema校验 ──失败──► 重试 (温度+0.1)
  │
  ▼ 成功
业务规则验证 ──失败──► 重试 (温度+0.1)
                    最多重试2次，温度上限0.3
  ▼ 成功
应用修改
```

**Schema校验**：使用 Draft7 JSON Schema，确保数据结构正确
**业务验证**：
- 坐标范围检查
- 棋子类型合法性
- 位置重叠检查
- 自定义棋子 type 冲突检查
- move.kind 合法性检查（jump/ray）

## 7. 规则引擎与对弈AI

### 7.1 规则引擎 (RuleEngine)

**文件**: `rule_engine.py`

**核心方法**:
- `get_valid_moves(piece, board_state)`: 获取棋子所有合法移动
- `is_in_check(side, board_state)`: 检查是否被将军
- `is_checkmate(side, board_state)`: 检查是否被将死
- `is_general_captured(side, board_state)`: 检查将帅是否被吃

**移动计算流程**:
```
pieces.json 的 moves[]
    ↓ 展开对称（sym）
每一条 move 定义
    ↓ 解析 where 条件
    ↓ 执行 jump/ray 原子
    ↓ 过滤条件不满足的位置
    ↓ 合并所有合法位置
最终合法移动列表
```

**_king_types 集合**: 初始化时构建，包含标准 `general` + 所有标记为 `is_king: true` 的自定义棋子。将军/将死/吃帅判断统一使用该集合，支持自定义国王棋子。

### 7.2 对弈AI (ChessAI)

**文件**: `chess_ai.py`

**算法**: Minimax + Alpha-Beta 剪枝
**评估函数**: 棋子价值 + 位置奖励 + 中心控制奖励

**难度等级**:
- easy: depth=2, randomness=0.3
- medium: depth=3, randomness=0.1
- hard: depth=4, randomness=0.0

**自定义棋子价值评估**:
- 遇到未知棋子类型时，调用 AI 动态评估价值
- 评估结果缓存，避免重复调用
- 通过 `token_stats_callback` 回调记录 token 消耗

### 7.3 机制引擎 (MechanismEngine)

**文件**: `mechanism_engine.py`

**设计理念**: 机制原语硬编码实现，AI通过修改JSON配置来组合使用这些原语（类比规则引擎的jump/ray原子体系），遵循"灵活编码"原则。

**5种原子化机制原语**：

| 原语 | 说明 | 数据路径 | 效果 |
|-----|------|---------|------|
| `skip_turns` | 跳过回合（冻结） | `/mechanisms/skip_turns/-` | 指定方跳过N回合，无法走棋 |
| `ai_control` | AI接管 | `/mechanisms/ai_control/-` | 指定方接下来N回合由AI代为走棋 |
| `random_moves` | 随机走棋 | `/mechanisms/random_moves/-` | 指定方接下来N步棋随机选择合法走法 |
| `extra_turns` | 额外回合 | `/mechanisms/extra_turns/-` | 指定方获得N次额外回合（连续走棋） |
| `move_limits` | 每回合步数限制 | `/mechanisms/move_limits/-` | 指定方每回合可以走N步 |

**核心方法**:
- `apply_pre_turn_mechanisms(board_state, side)`: 回合开始前应用机制（跳过回合检查、AI接管检查）
- `apply_post_move_mechanisms(board_state, side)`: 走棋后应用机制（消耗随机走棋、额外回合判定等）
- `get_active_mechanisms_summary(board_state)`: 获取当前激活的机制列表摘要
- `apply_personality_to_ai(chess_ai)`: 将性格配置应用到ChessAI实例

**机制组合能力**: AI可以自由组合多个原语实现复杂效果，例如：
- 冻结AI 2回合 = skip_turns(black, 2)
- 我的下两步棋由AI接管 = ai_control(red, 2)
- 我这步棋随便下 = random_moves(red, 1)
- 让AI变得狂暴 = aggressive性格 + random_moves各取所需

### 7.4 AI性格系统

**配置路径**: `rules.json → ai_difficulty.personality`

**预设性格类型**:

| 类型 | 说明 | 特点 |
|------|------|------|
| `normal` | 标准型 | 攻守平衡，标准AI |
| `aggressive` | 激进型 | 高进攻倾向，重视中心控制和过河兵 |
| `defensive` | 保守型 | 高防守倾向，重视将帅安全和棋子保护 |
| `random` | 随机型 | 低搜索深度，高随机度 |
| `custom` | 自定义型 | 自由调整所有参数 |

**性格参数**:
- `type`: 预设性格类型
- `aggressiveness`: 进攻倾向 0.0-1.0（影响位置评估权重）
- `conservatism`: 保守程度 0.0-1.0（影响防守评估权重）
- `randomness_override`: 覆盖默认随机度（null或0.0-1.0）
- `depth_override`: 覆盖默认搜索深度（null或正整数）
- `value_biases`: 棋子价值偏差 `{piece_type: bias_multiplier}`
- `custom_prompt`: 自定义提示词（字符串或null，预留扩展）

**评估函数中的性格影响**:
- 进攻倾向越高，过河兵、中心控制的权重越高
- 保守程度越高，将帅附近棋子的防守加分越高
- 棋子价值偏差可调整各棋子的重要性

## 8. HTML区段替换系统

### 8.1 设计理念

D2类修改通过**区段替换**方式修改 index.html，而非全量重写。优点：
1. **精准**：只改需要改的部分
2. **安全**：不会意外破坏其他区域
3. **高效**：AI只需输出目标区段内容，token消耗少

### 8.2 区段标记

在 index.html 中使用特殊注释标记可修改区段：
```html
<!-- SECTION: header -->
<header>...</header>
<!-- END_SECTION: header -->
```

### 8.3 可用区段

- `thinking_overlay`: AI思考遮罩
- `settings_modal`: 设置弹窗
- `logs_modal`: 日志弹窗
- `header`: 页头
- `board_section`: 棋盘区域
- `side_panel`: 侧边栏
- `input_section`: 输入区域
